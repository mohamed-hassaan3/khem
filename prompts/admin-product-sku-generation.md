# Admin product SKU generation

## Goal
Generate catalog-format SKUs from collection, product name, and volume on new-product forms; allow explicit regeneration on existing products; and resolve auto-generated SKU collisions on the server while preserving manual duplicate errors.

## Skills read
- None required. This is existing admin form/action logic and needs no database schema change.

## Existing code inspected
- `src/components/admin/ProductForm.tsx` (name, `collectionSlug`, `volumeMl`, `sku`, slug-touched pattern, payload, unsaved guard)
- `src/actions/admin/catalog.ts` (`createProduct`, `updateProduct`)
- `src/actions/admin/shared.ts` (existing SKU unique-violation message)
- `src/schemas/admin.ts` (create/update schemas and SKU validation)
- `src/app/[locale]/admin/products/[slug]/page.tsx`
- EN/AR dictionaries
- `supabase/sql/0015_orders.sql` and `supabase/sql/0062_sales_ledger.sql`

## Decisions and assumptions
- Add one pure shared helper in `src/lib/admin/sku.ts`; both create auto-fill and edit regeneration call it.
- Collection mapping is one exported constant: signature SIG, gemstone GEM, noir NOI, body-mist BOD, room-spray HOM, discovery-sets DIS, gift-sets GFT. Other slugs use their first three ASCII letters, uppercase, if available.
- Name code uses the first three ASCII letters of the first meaningful token, skipping leading filler words and format/type terms such as body, mist, room, spray, set/sets. Arabic-only names yield no name segment. Invalid/oversized volume is omitted, and the helper never returns an invalid or over-64-character SKU; return empty if no segment can be built.
- SKU warning must match stored facts: `OrderItem` snapshots product name and price but has no SKU column; `order_item_sales_ledger` snapshots SKU at sale. Warning therefore says future sales reporting uses the new SKU and past ledger rows retain their SKU snapshot; it must not claim order items store an old SKU.
- No migrations or writes to existing products.

## Implementation requirements
1. Keep the current SKU `AdminInput` label, required state, hint, and editability.
2. On create, regenerate from current name, collection slug, and volume whenever one of those inputs changes, until the editor manually changes SKU. Manual edit permanently stops automatic overwrites for that form session. Submit `skuAutoGenerated` to `createProduct` without putting it in the Product row; validate/confirm the flag server-side against the shared helper's base value.
3. Server create behavior: if the SKU is confirmed auto-generated and its SKU unique constraint conflicts, retry with `-2`, `-3`, etc., capped at 20 retries. Retry only a 23505 that names `Product_sku_key` (never slug/other unique errors) and let each failed create RPC transaction roll back. Before each suffix, truncate the base to keep the final SKU <= 64 characters and schema-valid. If the SKU was manually entered, preserve the existing “Another product already uses this SKU.” field error unchanged.
4. On edit, never auto-change SKU from name, collection, or volume. Add a small secondary “Regenerate from name” button next to the existing field. If helper output is empty or equals current SKU, do nothing. Otherwise set the form value only; saving remains the existing Save product action and the unsaved guard sees the new payload value.
5. On edit, check for another product using the proposed SKU with a server query excluding the current product slug, before updating. Return the same existing duplicate SKU field error. Keep the database unique constraint as a race-condition backstop.
6. Show a localized warning only when the edit SKU differs from the stored SKU: “Changing the SKU affects future sales reporting. Past sales-ledger entries keep the SKU recorded at sale.” Add button label and warning to EN/AR dictionaries and preserve RTL.
7. Do not touch stock, gallery, archive/delete, or unrelated flows.

## Security requirements
- Keep `requireAdmin()` first in each server action.
- Client auto-generated flags are untrusted; verify the submitted base SKU using the shared deterministic helper before allowing automatic suffix retries.
- Keep SKU schema validation and the unique database constraint intact.

## Acceptance criteria
- New product form updates generated SKU when name, collection, and volume change until SKU is manually touched.
- Generated values follow examples `KHEM-BOD-ONY-200` and `KHEM-GEM-SAP-050`; blank volume omits volume.
- Missing parts are omitted; Arabic-only name does not create invalid characters; empty output stays empty.
- Generated duplicate retries to `-2`, `-3`, etc.; manual duplicate retains existing error.
- Edit page never changes SKU automatically; explicit regeneration is dirty-guarded and saves only with Save product.
- Edit uniqueness excludes the product being edited and rejects another product's SKU.
- EN/AR labels and warning render correctly.
- Existing products' SKUs remain untouched and no migration is added.

4. Create two products generating the same SKU; verify second gets `-2`. Enter an existing SKU manually and verify the existing duplicate error.
5. Leave volume blank and verify no volume segment.
6. Use an Arabic-only name and verify no invalid SKU is produced.
7. On edit, change name/collection/volume and verify the SKU remains; regenerate, observe warning and unsaved guard, save, and verify another product's SKU is rejected.
8. Verify button and warning in English and Arabic RTL.
